geai — архитектура ядра

Автономный агент отладки и разработки внутри IntelliJ IDEA / Android Studio. Документ описывает три кита архитектуры: GRACE context engine (граф + якоря + спеки), agent loop (цикл исполнения) и управление контекстом (сборка, эвикция, компрессия, персистентность). Все факты раздела 3 сверены с кодом; ссылки даны в формате file:line.

1. Архитектура GRACE context engine

GRACE — Graph-RAG Anchored Code Engineering. Цель: вынести интеллект из модели в строительные леса — граф, якоря, спеки, детерминированные резолверы — так, чтобы даже дешёвая LLM (Qwen, DeepSeek) умела навигировать и понимать проект на высоком уровне, а крупные модели подключались как авторы кода, а не как костыль для понимания. GRACE не привязан ни к языку, ни к IDE: привязка локализована в резолверах (SPI); граф, спеки и доктрина при смене хоста (VS Code, LSP, CLI) не меняются. Первоисточник: docs/GRACE_ARCHITECTURE.md.

1.1 Главный принцип — «lookup, не recall»

Слабые модели галлюцинируют факты (сигнатуры, пути, контракты), потому что вспоминают их по памяти. GRACE превращает каждый такой факт в операцию «спроси граф → резолвни якорь → подставь вывод инструмента». Модель не обязана знать — она обязана следовать правилам и подставлять ground truth.

Интеллект агента = качество графа + детерминизм резолверов + строгость доктрины. Качество модели — множитель сверху, не фундамент.

1.2 Две категории знания

A. Замысел / инвариантB. Контракт / реальность кода
Чтото, что нельзя вывести из кода: инварианты, формулы, бизнес-правила, state-машины сигнатуры API, DTO, схемы, символы — то, чем владеет код
Хранениеполноценный XML в spec/ (источник истины, в VCS) якорь-ссылка, не копия
Как агент берётчитает дословнорезолвит в живой источник (PSI/OpenAPI)
Дрейфревьюится людьмидетектируется механически (hash якоря)
Железное правило: Категория Б никогда не копируется в текст — ни в спеку, ни в ответ модели. Только якорь + резолв. Это убивает рассинхрон на корню.

1.3 Слои хранения

spec/                      # Категория A — авторитетные XML-спеки, в VCS
  <domain>/<name>.spec.xml
.geai/knowledge.xml        # оси знания NAV/STYLE/TECH/LESSON

Граф кода не материализуется и не хранится — структура (классы, методы, иерархия, соседи) читается на лету из PSI/индекса IntelliJ (PsiStructure), поэтому всегда актуальна и не требует пересборки. Контент Категории Б нигде не кешируется — только ref, резолвящийся в живой источник по запросу.

1.4 Узлы и рёбра графа

Узлы делятся на сущности кода (анкерные, категория Б) и узлы знания/замысла (контентные, категория А):

ГруппаУзлы
Сущности кода (Б)MODULE, PACKAGE, FILE, SYMBOL (psi-anchor), CONTRACT (openapi/proto/graphql), ENTRYPOINT, TEST
Знание и замысел (А)INVARIANT, FORMULA, STATE_MACHINE, INTENT, POLICY/RULE, STYLE, TECH, LESSON

Рёбра: contains, defines, calls, reads/writes, implements/extends, depends_on, refs, tested_by, governed_by, violates, supersedes. Ключевое ребро — governed_by: оно связывает код с правилом, которое его регулирует; автор-модель, трогая узел, обязана подтянуть все governed_by и применить их как ограничения.

1.5 Якоря и Resolver SPI

Якорь — URI-подобная ссылка scheme:locator. На каждую схему — свой резолвер (AnchorResolver SPI: resolve(ref, project) → kind, signature, location, content, hash).

СхемаРезолвит вХост
psi:<fqName>[#member]сигнатура/доки/file:line символаIntelliJ (PSI)
sym:<lsp-id>то же через LSPне-IDE хосты
file:<path>[:a-b]диапазон строклюбой
openapi:<doc>#<json-pointer>живой кусок сгенерённого OpenAPIстек с OpenAPI
proto: / graphql: / jsonschema:соответствующий контрактпо наличию
git:<rev>:<path>запиненная историческая истиналюбой

IntelliJ-хост регистрирует PSI-резолверы; будущий VS Code/CLI-хост — LSP-резолверы. Граф, спеки и доктрина при этом не меняются — это и есть универсальность.

1.6 Graph-RAG: сборка context bundle

Retrieval — детерминированный обход графа, не векторный «авось». На каждый запрос PsiStructure собирает эфемерный подграф из живого PSI (структура) + спек (governance), и по нему идёт обход:

1. Seed — стартовые узлы по имени/тегу/оси (из запроса задачи) 2. Expand — N хопов по типам рёбер (calls, governed_by, refs, tested_by) 3. Resolve — для анкерных узлов дёрнуть resolve_ref → ЖИВОЙ контент Категории Б 4. Pack — bundle: спеки A дословно + контракты B живьём + правила + соседи

Ранжирование — Ranker SPI с дефолтным DeterministicRanker (hops + term-overlap + kind-prior); векторный ранкер плагинится в тот же шов (флаг graceVectorRanker), базовый обход детерминирован.

1.7 Двухуровневая маршрутизация моделей

TierМоделиДелаетОбъём
NavigatorQwen, DeepSeek, Haikuобход графа, резолв якорей, сборка bundle, локализация, механические правки~90% операций, копейки
AuthorQwen-max, Claude Opusнаписание кода/рефактор с применением правил, трейд-оффы~10%, дорого, по делу

Тиринг opt-in (tieredRoutingEnabled, navigatorModel): цикл идёт на дешёвой navigator-модели, авторинг кода — через escalate_author на сильной main-модели. Navigator готовит минимальный точный bundle → Author пишет: дорогая модель не тратит токены на «понять проект» — только на «написать правильно».

1.8 Детект дрейфа спек

Так как категория Б анкерная и хэшированная, geai механически проверяет согласованность спек↔код: каждый ref всё ещё резолвится; contentHash живого резолва совпадает с сохранённым (иначе узел stale); правила, на которые ссылается код, существуют. spec_validate гоняется после правок и в CI и репортит OK/DRIFT/BROKEN/NO-BASELINE. Именно это позволяет доверять слабой модели: она не может молча рассинхронизировать проект.

1.9 Инструменты и доктрина

Navigator (read, дёшево): graph_query (символы по имени вживую из индекса + governing-спеки), graph_neighbors (соседи узла: PSI + governed_by/refs), resolve_ref, context_bundle (seed→expand→resolve→pack — ключевой), spec_lookup/spec_list, spec_validate. Author/mutating: spec_record (create-or-update с CAS по version), существующие edit_file/write_file/run_command/debug-*. Отдельного graph_reindex нет — пересобирать нечего, структура живая.

Доктрина (SystemPrompt): любой вопрос «где/что/почему» → сперва graph_query/context_bundle, не grep; факты категории Б → всегда resolve_ref, никогда не по памяти; перед написанием кода — подтянуть governed_by и применить как жёсткие ограничения; после правок — spec_validate + сборка/тесты; при неудаче — записать LESSON.

2. Agent loop

Ядро исполнения — AgentLoop (src/main/kotlin/com/github/saeldrit/geai/agent/AgentLoop.kt), единственный нативный движок (CLI-движок удалён в Ф6). Точка входа — GeaiAgentService.submit() (GeaiAgentService.kt:78-121): ход выполняется как фоновая Task.Backgroundable с индикатором прогресса, метка Local History ставится перед ходом (для revert), сессия сохраняется на каждом ToolFinished (с троттлингом) и финально по Done/Error/Cancelled.

2.1 Обзор хода (turn)

Один вызов run(session, userText, listener, indicator) — это один «ход» пользователя, внутри которого крутится итерационный цикл LLM ⇄ инструменты. Перед циклом: строится системный промпт (SystemPrompt.build, lean-вариант для суб-агентов, AgentLoop.kt:134), парсится slash-команда, подтягивается подсказка о прошлых сессиях (PastSessions.hint, только для первого сообщения сессии, AgentLoop.kt:136-140) и собирается GRACE-бандл, который однократно вшивается в транскрипт сразу после задачи (AgentLoop.kt:141-148, подробно — §3.1).

2.2 Итерационный цикл

while (true): // AgentLoop.kt:178+ 1. проверка cancel / maxIterations / токен-бюджета суб-агента 2. эвикция + компрессия транскрипта (§3.2, §3.3; skip при активном debug) 3. LLM-запрос: system + tools + транскрипт + trailing-контекст (§3.1) 4. stream-ответ → AssistantText / Reasoning события 5. есть tool_use? → исполнить инструменты, добавить tool_result, continue нет tool_use? → ход завершён (финальный ответ)

Каждая итерация пересылает весь транскрипт, поэтому экономика хода определяется кешируемостью префикса и леанностью транскрипта — этому посвящён весь раздел 3.

2.3 Инструменты по требованию (tool groups)

Реестр — GeaiToolset (tools/GeaiToolset.kt): ядровые группы (файлы, поиск, GRACE, knowledge) объявлены сразу, тяжёлые группы (debug/run/specs/selfmod) подключаются инструментом load_tools в activeGroups (AgentLoop.kt:163-165) — это экономит контекст: описания десятков инструментов не оплачиваются, пока не нужны. Если при старте хода уже есть активная debug-сессия, группа debug активируется автоматически (AgentLoop.kt:165).

2.5 Суб-агенты (delegate)

Инструмент delegate порождает read-only суб-агента со своим чистым контекстом: тот же AgentLoop, но с профилем isSubAgent — lean-промпт, свой maxIterations и токен-бюджет (AgentLoop.kt:149-150), без мутирующих инструментов. Суб-агенту передаётся текущий GRACE-бандл (currentBundle, AgentLoop.kt:172) и топ-10 заметок родителя (§3.5); отчёт ограничен ~6000 символов — родитель получает выжимку, а не сырые файлы. Количество делегирований на ход ограничено (delegationCount, AgentLoop.kt:166).

2.6 Завершение хода

Нормальное завершение — ответ ассистента без tool_use. Аварийные пути (summarizeAndFinish) — лимит итераций, бюджет суб-агента: агент подводит итог по уже сделанному и отдаёт управление. Все пути ведут к событиям Done/Error/Cancelled для слушателя (UI-панель или HubTaskListener, §3.7) и финальному сохранению сессии (GeaiAgentService.kt:99,115). Метрики хода (итерации, токены, компрессии) собирает AgentMetrics (AgentLoop.kt:152).

3. Управление контекстом

Контекстное окно — главный ресурс агента: каждая итерация цикла пересылает весь транскрипт. Подсистема управления контекстом решает четыре задачи: собрать запрос кеш-дружелюбно (§3.1), не платить за устаревшие выводы инструментов (§3.2), пережить длинные ходы без потери знания (§3.3) и сохранить всё на диск (§3.6). Все факты сверены с кодом.

3.1 Сборка контекста хода — послойная схема запроса

Запрос к LLM строится слоями от самого стабильного (кешируемого провайдером) к самому изменчивому:

┌───────────────────────────────────────────────────────────────┐ │ 1. System prompt + описания инструментов [кеш: стабилен │ │ (SystemPrompt.build, lean для суб-агентов) весь ход] │ ├───────────────────────────────────────────────────────────────┤ │ 2. Транскрипт: задача пользователя │ │ + GRACE-бандл, вшитый ОДНОКРАТНО после задачи │ │ + PastSessions.hint (подсказка о прошлых сессиях) │ │ + вся история итераций (assistant / tool_use / tool_result) │ │ [кеш: rolling breakpoint, растёт] │ ├─────────────── rolling cache breakpoint ──────────────────────┤ │ 3. Volatile-хвост (НЕ кешируется, меняется каждую итерацию): │ │ — заметки агента │ │ + bundleSuffix (только после request_context среди хода) │ └───────────────────────────────────────────────────────────────┘

Однократное вшивание бандла. GRACE-бандл + PastSessions.hint склеиваются и добавляются в транскрипт одним user-сообщением сразу после задачи (AgentLoop.kt:141-148). Комментарий в коде объясняет экономику: внутри кешируемого префикса rolling breakpoint бандл оплачивается свежим один раз и дальше подаётся из кеша на каждой из ~20 итераций хода; трейлинг-копия после breakpoint никогда бы не кешировалась и оплачивалась бы заново каждую итерацию. Поэтому bundleSuffix — трейлинг-бандл — пуст и заполняется только редким request_context посреди хода (AgentLoop.kt:169-173).

Volatile-блок заметок. appendTrailingContext (AgentLoop.kt:680-695) добавляет после rolling cache breakpoint блок <your_notes> — до 50 актуальных заметок (MAX_NOTES_RETAINED, AgentLoop.kt:1098). Заметки меняются каждую итерацию, поэтому живут в некешируемом хвосте — их изменение не инвалидирует кеш транскрипта.

PastSessions.hint подтягивается только когда сессия практически пуста (session.messages.size <= 1) и не для суб-агентов (AgentLoop.kt:136-140): агенту показываются заголовки/итоги возможно релевантных прошлых сессий, чтобы не расследовать заново уже решённое.

Эвристика смены задачи. В начале хода новый запрос пользователя сравнивается с текущей задачей; при детекте переключения scratchpad чистится по приоритетам: LOW-заметки сбрасываются, старые NORMAL отсекаются, CRITICAL сохраняются — с уведомлением «🧹 Task switch: dropped … kept …» (AgentLoop.kt:120-124).

3.2 Эвикция устаревших выводов инструментов

ToolResultEvictor (context/ToolResultEvictor.kt) — механическая, без LLM, замена устаревших tool_result на короткие заглушки. Мотивация (комментарий ToolResultEvictor.kt:7-19): 40k-символьный файл, прочитанный 20 ходов назад, оплачивается на каждом последующем запросе, хотя модель давно извлекла из него нужное; компрессор же срабатывает только у лимита окна и стоит вызова summarizer-а.

КонстантаЗначениеСмыслГде
MIN_EVICTABLE_CHARS600результаты ≤600 символов не трогаются — заглушка не окупитсяToolResultEvictor.kt:24
STUB_HEAD_CHARS200сколько «головы» оригинала выживает в заглушке (обрез по границе строки)ToolResultEvictor.kt:27
MIN_TOTAL_GAIN_CHARS16 000гистерезис: батч не запускается, пока нельзя вернуть ≥16k символов разомToolResultEvictor.kt:32
MIN_TRANSCRIPT_CHARS60 000пол активации: ниже — эвикция не окупает промах кеша, малые сессии не трогаютсяToolResultEvictor.kt:37

Гистерезисные батчи. Каждый батч переписывает префикс транскрипта и тем самым инвалидирует prompt-кеш провайдера на весь диалог — поэтому батчи должны быть редкими и крупными: сначала сухой подсчёт выигрыша, и только если gain ≥ 16k — фактическая замена (ToolResultEvictor.kt:54-91). Граница «свежести» — индекс K-го с конца assistant-сообщения (ToolResultEvictor.kt:97-106); парность tool_use/tool_result никогда не рвётся — меняется только контент блока.

Формат заглушки (ToolResultEvictor.kt:129-137): первые ~200 символов оригинала (для read_file это заголовок «// path (lines a-b of N)», для run_command — команда и exit code), затем маркер:

…[stale tool output evicted: N chars of stale output dropped to keep context
lean. Durable findings are in SESSION MEMORY / your notes; re-read the specific
range or re-run the command if you truly need this data again]

Маркер служит и защитой от повторной эвикции (ToolResultEvictor.kt:122-123), и явной подсказкой агенту: узкое повторное чтение — штатный путь восстановления, знание не потеряно (оно в notes / SESSION MEMORY).

3.3 Компрессия транскрипта

ContextCompressor (context/ContextCompressor.kt) — lossy-сжатие, срабатывающее по водяным знакам: триггер при заполнении 70% бюджета транскрипта, цель — ужать до 50% (ContextCompressor.kt:30,38). Хвост из последних сообщений (адаптивно 6–14 в зависимости от бюджета, ContextCompressor.kt:47-48,161-164) сохраняется дословно; всё старше сворачивается.

Пайплайн: TranscriptAnalyzer строит детерминированный дайджест (SESSION MEMORY ledger: файлы, вызовы, находки, выводы), затем — если есть summarizer — старый сегмент рендерится в текст и сжимается LLM по доктрине SemanticCompressor.DOCTRINE (context/SemanticCompressor.kt:12-36): строгий JSON с полями taskDescription/findings/decisions/codeChanges/openQuestions/nextSteps/userPreferences, обязательное сохранение всех file:line, лимит 2000 токенов (SemanticCompressor.kt:38). Итоговое synthetic-сообщение: [CURRENT ACTIVE TASK …] + recap + [SESSION MEMORY …] (ContextCompressor.kt:127-143).

Каскад fallback-ов (метод фиксируется в метриках, ContextCompressor.kt:144-157):

МетодКогда
summarizeLLM-recap удался — ledger + семантическая выжимка
ledgersummarizer недоступен/вернул пусто — только детерминированный дайджест
truncateрезультат всё ещё не влез в бюджет — механическое усечение (сначала TOOL-блоки, затем ASSISTANT/USER, затем drop сообщений; ContextCompressor.kt:189-200)

Особые режимы: при активной debug-группе компрессия пропускается (skipCompression = activeGroups.contains("debug"), AgentLoop.kt:199) — нельзя терять контекст живой отладочной сессии. При overflow-ошибке провайдера выполняется forced-compress до половины окна с повтором запроса (AgentLoop.kt:307-321, счётчик contextOverflowRetries). Ручная команда /compact сжимает транскрипт до COMPACT_TARGET_TOKENS = 48 000 токенов (GeaiAgentService.kt:26).

3.5 Notes / scratchpad / skills

Scratchpad — инструмент note, позволяющий агенту хранить промежуточные факты между итерациями без повторного чтения файлов. Заметки живут в памяти сессии и не переживают перезапуск IDE (для持久ного знания — knowledge store, §3.6). Три уровня приоритета: CRITICAL (переживают компрессию и смену задачи), NORMAL (переживают компрессию), LOW (сбрасываются при смене задачи). В запрос к LLM заметки вшиваются блоком <your_notes> после rolling cache breakpoint — максимум MAX_NOTES_RETAINED = 50 штук, отсортированных по приоритету (AgentLoop.kt:1098). При превышении лимита старые LOW-заметки отбрасываются с явным сообщением «showing X of Y».

Эвристика смены задачи (AgentLoop.kt:120-124): при детекте переключения (новый запрос не похож на текущую задачу) LOW-заметки сбрасываются, старые NORMAL отсекаются, CRITICAL сохраняются — агент получает уведомление с количеством потерянных/сохранённых записей.

Skills —持久ные пользовательские предпочтения, сохраняемые в .geai/skills/*.json (SkillStore.kt:38-39). Лимит MAX_SKILLS = 20 (SkillStore.kt:25). Семь доменов конфликтов (indentation, language, style, verbosity, comments, async, error handling) — при сохранении нового навыка проверяется пересечение с существующими, и пользователь получает предупреждение. Skills рендерятся в <user_preferences> XML, сгруппированные по категориям, и вшиваются в system prompt — они переживают перезапуск IDE, в отличие от scratchpad.

3.6 Персистентность .geai/

Вся持久ная состояние geai хранится в директории <project>/.geai/:

ПутьСодержимоеФормат
.geai/sessions/*.jsonсессии агента (транскрипт + метаданные)JSON
.geai/knowledge.xmlиндекс знаний (NAV/STYLE/TECH/LESSON)XML, CAS по version

GeaiSessionStore (GeaiSessionStore.kt:24-33): атомарная запись (временный файл → Files.move(REPLACE_EXISTING)); saveAsync() — коалесцирующая асинхронная запись: если очередь забита, сохраняется только последний снимок. loadMostRecent() берёт свежайший .json по last-modified time. Fallback-путь при недоступности проектовой директории: PathManager/geai/<hash>/sessions/.

GeaiKnowledgeStore (GeaiKnowledgeStore.kt:26-31): единый XML-файл; каждая запись — ось (NAV/STYLE/TECH/LESSON), теги, заголовок, тело, location, version. put(expectedVersion) — CAS-апдейт: при несовпадении версии возвращается Conflict(currentVersion). In-memory кеш инвалидируется при внешних правках файла (invalidateCache()). query(axis?, tags, text?) фильтрует по оси, совпадению тегов и полнотекстовому поиску по заголовку/телу/тегам/локации.

Доктрина: .geai/ попадает в .gitignore — сессии и знания не коммитятся в репозиторий проекта (они персональны). Знания проекта (категория А) хранятся в spec/ и коммитятся; знания агента (LESSON, STYLE) — в .geai/ и не коммитятся.

3.7 Hub connector

Hub — координатор распределённой разработки: централизованная точка, где создаются задачи и собираются результаты. geai-плагин подключается как spoke (вассал) через WebSocket.

Протокол. Версия 1.2.0 (HubService.kt:29). Идентификатор spoke: geai-<ideType>-<projectName>-<hash8> (HubService.kt:67-71); capabilities определяются типом IDE: webstorm → frontend, android-studio → android, иначе → backend (HubService.kt:176-180). Сообщения — полиморфный sealed class WsMessage с @SerialName дискриминаторами: Inbound: HelloAck, TaskAssign, TaskCancel, FileRequest, Ping/Pong. Outbound: SpokeHello, SpokeStatus, SpokeEvent, SpokeMetrics, AgentProgress, TaskLog, TaskResult, FileContent, ContractPublish/ContractReject.

Транспорт. java.net.http.WebSocket, connect timeout 8s (HubClient.kt:93-96). Авто-реконнект с экспоненциальным backoff (1 << min(n,5)).coerceAtMost(30) секунд (HubClient.kt:120-126). Heartbeat ping каждые 25 секунд (HubClient.kt:130-133). Порядок сообщений гарантируется цепочкой sendChain CompletableFuture (HubClient.kt:77-85). Состояние: HubState sealed — Disconnected / Connecting / Connected(hubVersion) / Error(message).

Исполнение задачи. При TaskAssign запускается HubTaskListener (HubService.kt:476+), который мостит AgentEvent → Hub: progress %, лог-строки, пути артефактов, финальный результат. Задача выполняется тем же AgentLoop, что и интерактивный ход — с теми же инструментами, GRACE-бандлом, эвикцией и компрессией. Авто-подключение при старте проекта (hubAutoConnect = true, GeaiSettings.kt:116) позволяет IDE мгновенно стать spoke без ручного действия.

File pull. Hub может запросить содержимое файла, который произвёл агент (FileRequest → FileContent), с ограничением MAX_FILE_BYTES = 25 MB (HubService.kt:31) и проверкой, что путь внутри проекта.
