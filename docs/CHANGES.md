# Что было сделано с geai — простым языком

## v0.0.82 — Hub file pull, append mode, brace-balanced JSON, incremental authoring

### 1. HubProtocol + HubService — File pull (запрос файлов из хаба)
Hub теперь может запрашивать содержимое файлов, произведённых агентом. Добавлены сообщения
`FileRequest` и `FileContent` в протокол. HubService проверяет, что путь внутри проекта и
файл ≤ 25 MB, отдаёт base64 с автоматическим MIME.

### 2. WriteFileTool — append mode (инкрементальная запись)
Новый параметр `mode: "append"` позволяет дописывать в конец файла вместо перезаписи.
Агент может писать крупные документы частями (skeleton → section by section), и каждая часть
сразу сохраняется на диск.

### 3. HubService — brace-balanced JSON extraction
Старый regex для извлечения JSON из ответа LLM обрезал вложенные объекты на первом `}`.
Новый `balancedJsonSpan()` отслеживает depth + string-литералы → корректный парсинг
вложенного JSON.

### 4. SystemPrompt — incremental authoring doctrine
Новая секция «Authoring a large NEW file» учит агента: не писать гигантский файл за раз,
а строить skeleton → append section by section. Каждый вызов персистентен, прерывание не
теряет прогресс.

### 5. GeaiSettings — hubAutoConnect = true
Spoke теперь подключается к хабу автоматически при старте проекта (было false → нужен был
ручной клик).

### 6. docs/architecture-geai.html — полная документация архитектуры
HTML-документ §3.4–3.7: лимиты и калибровка, scratchpad/skills, персистентность .geai/,
hub connector.

## Проблема

Агент geai работал **крайне медленно**: простое чтение файлов могло занимать больше часа.
Агент «крутился» — читал файлы один за другим, не останавливался, повторял одни и те же шаги.
Production readiness: 4 из 10.

---

## Что исправлено (6 файлов)

### 1. SystemPrompt.kt — Агент научился быстро работать

**Проблема:** Агент не знал, когда остановиться. Читал файлы «на всякий случай» по одному за ход.
Один файл за ход → 20+ ходов → 1+ час на простой таск.

**Что сделано:** Добавили раздел «Speed strategy» в системный промпт — инструкции для LLM:
- Читай файлы пачками (batch) — до 5 файлов за ход
- Останавливайся, когда достаточно данных для ответа (3-5 ходов)
- Следуй чёткому дереву решений для диагностики багов

**Эффект:** 2-5 ходов вместо 20+. Субъективно: минуты вместо часа.

---

### 2. ContextCompressor.kt — Компрессор не давил сам себя

**Проблема:** Две проблемы в одном:
1. Порог SAFETY был 0.6 — компрессор позволял накопить 112K токенов прежде чем сжимать.
2. Eager truncation (обрезка старых tool_result) запускалась первой и безусловно. После обрезки транскрипт оказывался в рамках бюджета → суммаризатор (LLM, складывающий историю в краткую сводку) **никогда не вызывался**. Старые данные просто терялись.

**Что сделано:**
- SAFETY снижен до 0.5 → суммаризация срабатывает раньше
- Логика исправлена: сначала проверяем размер **оригинала**, потом решаем нужна ли суммаризация. Eager truncation применяется к **результату** суммаризации, а не вместо неё

**Эффект:** Суммаризатор работает корректно — сжимает историю, сохраняя находки и решения. Транскрипт не раздувается.

---

### 3. ToolSpec.kt — Схемы инструментов больше не парсятся каждый запрос

**Проблема:** Каждый раз когда агент отправлял запрос к LLM, JSON-схемы всех инструментов (20+ штук) парсились из строки в объект. Это происходило на **каждом ходу**.

**Что сделано:** Добавлено ленивое кеширование:
```kotlin
val parsedSchema: JsonElement by lazy { JsonSupport.parseElement(parametersJsonSchema) }
```
Парсинг происходит один раз, потом результат переиспользуется.

**Эффект:** Экономия Gson-парсинга на каждом запросе. Мелочь, но на длинных сессиях складывается.

---

### 4. AnthropicClient.kt и OpenAiCompatibleClient.kt — SSE-ошибки больше не замалчиваются

**Проблема:** При обработке потокового ответа от LLM (SSE) стоял `catch(Exception)`, который ловил **всё** — включая баги в самом коде (NPE, IndexOutOfBounds). Баги молча проглатывались, агент продолжал работать с неполными данными.

**Что сделано:** Строгий фильтр — ловим только ошибки парсинга данных:
- `JsonSyntaxException` — некорректный JSON от сервера
- `ClassCastException` — неожиданный тип поля
- `NumberFormatException` — не число там где ожидали

Всё остальное (программные баги) **пробрасывается** наружу — сразу видно если что-то сломалось.

**Эффект:** Баги в обработке SSE больше не прячутся. Если что-то пойдёт не так — ошибка видна, а не тихо игнорируется.

---

### 6. AgentLoop.kt — Защита от бесконечных циклов

**Проблема:** Агент мог повторять один и тот же шаг снова и снова — вызывать тот же инструмент с теми же аргументами, получать тот же результат, и пытаться снова.

**Что сделано:**
- **Stuck-loop detection:** Кольцевой буфер из 5 последних хешей шагов. Если новый шаг совпал с одним из предыдущих — агент получает предупреждение «you're looping, take a different approach»
- **kb_lookup suppression:** Если знаниевая база возвращает пустой результат 3 раза подряд — вызов прекращается
- **Delegate error handling:** Ошибки в под-агентах (delegates) теперь логируются вместо того, чтобы проглатываться

**Эффект:** Агент не застревает в бесконечных циклах. Если повторяет шаг — получает явный сигнал остановиться.
