# GRACE — Graph-RAG Anchored Code Engineering

Архитектура ядра geai. Цель: **вынести интеллект из модели в строительные леса** — граф,
якоря, спеки, детерминированные резолверы — так, чтобы даже слабая/дешёвая LLM (Qwen, DeepSeek)
умела навигировать, понимать и строить проект на высоком уровне. Крупные модели (Qwen-max,
Claude 4.8) подключаются как **авторы кода**, а не как костыль для понимания.

Принцип универсальности: geai сегодня живёт в IntelliJ, но GRACE не привязан ни к языку, ни к
стеку, ни к IDE. Привязка локализована в **резолверах** (SPI); сменив хост (VS Code, LSP, CLI),
меняем только их — граф, спеки и доктрина не меняются.

---

## 0. Главный принцип — «lookup, не recall»

Слабые модели галлюцинируют факты (сигнатуры, пути, контракты), **потому что вспоминают их по
памяти**. GRACE превращает каждый такой факт в операцию «спроси граф → резолвни якорь →
подставь вывод инструмента». Модель не обязана *знать* — она обязана *следовать правилам и
подставлять ground truth*. Это и есть рычаг, который вытягивает дешёвую LLM.

> Интеллект агента = качество графа + детерминизм резолверов + строгость доктрины.
> Качество модели — множитель сверху, не фундамент.

---

## 1. Две категории знания (фундамент)

| | **A. Замысел/инвариант** | **B. Контракт/реальность кода** |
|---|---|---|
| Что | то, что **нельзя вывести из кода**: инварианты, формулы, бизнес-правила, замысел, state-машины | сигнатуры API, DTO, схемы, символы — то, **чем владеет код** |
| Хранение | полноценный XML в `spec/` (источник истины) | **якорь-ссылка**, не копия |
| Как агент берёт | читает дословно | **резолвит в живой источник** (PSI/OpenAPI/proto/types) |
| Дрейф | ревьюится людьми | **детектируется механически** (hash якоря) |

Правило железное: **Категория Б никогда не копируется в текст** — ни в спеку, ни в ответ
модели. Только якорь + резолв. Это убивает рассинхрон на корню.

---

## 2. Слои хранения

```
spec/                      # Категория A — авторитетные XML-спеки, в VCS
  <domain>/<name>.spec.xml
.geai/graph/               # производный граф (узлы+рёбра+хэши якорей), rebuildable
  nodes.xml  edges.xml     # НЕ источник истины для B — хранит указатели и хэши, не контент
.geai/knowledge.xml        # существующие оси (эволюционируют в узлы графа)
```
`spec/` коммитится (это замысел). `.geai/graph/` производный — пересобирается из код+спеки,
можно gitignore. Контент Категории Б **нигде не кешируется** — только `ref` + `contentHash`
на момент индексации (для детекта дрейфа).

---

## 3. Узлы графа (оси)

Эволюция текущих `NAV/STYLE/TECH/LESSON` в полную таксономию. Узлы делятся на **сущности кода**
(в основном Категория Б, анкерные) и **узлы знания/замысла** (Категория А, контентные).

### Сущности кода (анкерные, B)
- `MODULE` / `PACKAGE` — структурные контейнеры
- `FILE` — файл (`file:` anchor)
- `SYMBOL` — класс/интерфейс/функция/поле (`psi:`/`sym:` anchor → сигнатура + `file:line`)
- `CONTRACT` — endpoint/DTO/схема (`openapi:`/`proto:`/`graphql:`/`jsonschema:` anchor)
- `ENTRYPOINT` — main/route/handler
- `TEST` — тест (`psi:` anchor), связан `tested_by`

### Знание и замысел (контентные, A)
- `INVARIANT` — что обязано всегда выполняться («деньги не отрицательны»)
- `FORMULA` — вычисление/бизнес-логика
- `STATE_MACHINE` — разрешённые переходы
- `INTENT` — *почему* так спроектировано
- `POLICY` / `RULE` — **как применять фичи/фиксы** (правила, по которым автор пишет код)
- `STYLE` — конвенции проекта
- `TECH` — факты стека/сборки/инвариантов окружения
- `LESSON` — анти-паттерны, жёсткие самоограничения

### Рёбра (типизированные связи)
`contains`, `defines`, `calls`, `reads`/`writes`, `implements`/`extends`, `depends_on`,
`refs` (якорь), `tested_by`, `governed_by` (символ/контракт ← инвариант/полиси),
`violates` (находка дрейфа/линта), `supersedes` (версионирование).

Ключевое ребро для твоего замысла — **`governed_by`**: оно связывает кусок кода с правилом,
которое его регулирует. Автор-модель, трогая узел, обязана подтянуть все `governed_by` и
применить их как ограничения.

## 4. Якоря и Resolver SPI (механизм универсальности)

Якорь — URI-подобная ссылка `scheme:locator`. На каждую схему — свой резолвер.

| Схема | Резолвит в | Хост |
|---|---|---|
| `psi:<fqName>[#member]` | сигнатура/доки/`file:line` символа | IntelliJ (PSI) |
| `sym:<lsp-id>` | то же через LSP | не-IDE хосты |
| `file:<path>[:a-b]` | диапазон строк | любой |
| `openapi:<doc>#<json-pointer>` | живой кусок сгенерённого OpenAPI (`/v3/api-docs`) | любой стек с OpenAPI |
| `proto:` / `graphql:` / `jsonschema:` / `ts:` | соответствующий контракт | по наличию |
| `git:<rev>:<path>` | запиненная историческая истина | любой |

```kotlin
interface AnchorResolver {
    val scheme: String
    fun resolve(ref: String, project: Project): ResolvedAnchor   // kind, signature, location, content, hash
}
```
IntelliJ-хост регистрирует PSI-резолверы; будущий VS Code/CLI-хост — LSP-резолверы. **Граф,
спеки и доктрина не меняются** — это и есть универсальность. Пример якоря в спеке:

```xml
<contract ref="openapi:main#/paths/~1api~1v1~1goals/post"/>
<governed-by ref="psi:com.app.goal.GoalService#create"/>
```

## 5. Graph-RAG: сборка контекста

Retrieval = детерминированный обход графа, не векторный «авось»:

1. **Seed** — стартовые узлы по имени/тегу/оси (из запроса задачи).
2. **Expand** — N хопов по выбранным типам рёбер (`calls`, `governed_by`, `refs`, `tested_by`).
3. **Resolve** — для всех анкерных узлов дёрнуть `resolve_ref` → **живой** контент Категории Б.
4. **Pack** — собрать **context bundle**: спеки A дословно + резолвленные контракты B +
   правила/инварианты/уроки + соседние символы. Минимально и актуально.

Этот bundle — то, что уходит автор-модели. Дешёвая модель **собирает** bundle (механика по
графу), дорогая — **пишет код** по нему. Векторный RAG опционально добавляется как ранкер для
больших графов, но базовый обход детерминирован.

## 6. Двухуровневая маршрутизация моделей

| Tier | Модели | Делает | Объём |
|---|---|---|---|
| **Navigator** | Qwen, DeepSeek, Haiku | обход графа, резолв якорей, сборка bundle, `spec_validate`, локализация, механические правки | ~90% операций, копейки |
| **Author** | Qwen-max, Claude Opus 4.8 | написание кода/рефактор с применением правил, оценка трейд-оффов | ~10%, дорого, по делу |

Navigator готовит минимальный точный bundle → Author пишет. Так дорогая модель не тратит токены
на «понять проект» (это сделал граф) — только на «написать правильно». Максимальная экономия
при максимальном качестве. Маршрутизация — настройка: какая модель на каком tier.

---

## 7. Детект дрейфа — страховка доверия к дешёвой модели

Так как Б анкерная и хэшированная, geai **механически** проверяет согласованность спек↔код:
- каждый `ref` всё ещё резолвится (контракт не удалён/переименован);
- `contentHash` живого резолва == сохранённого → иначе узел `stale`;
- инварименты/полиси, на которые ссылается код, существуют.

`spec_validate` гоняется после правок и в CI. Именно это позволяет **доверять** слабой модели:
она не может молча рассинхронизировать проект — рассогласование ловится детерминированно.
Опция: авто-ребинд якоря при ренейме по идентичности символа (fqName + signature hash).

## 8. Инструменты geai (новые)

**Navigator (read, дёшево):**
- `graph_query` — узлы по оси/тегу/имени/связи → id + краткое описание
- `graph_neighbors` — раскрыть рёбра узла (`calls`/`governed_by`/`refs`…)
- `resolve_ref` — резолв якоря в живой ground truth (через Resolver SPI)
- `context_bundle` — собрать минимальный bundle под задачу (seed→expand→resolve→pack) ← ключевой
- `spec_lookup` / `spec_list` — читать спеки A
- `spec_validate` — детект дрейфа

**Author / сопровождение (mutating, под апрувом):**
- `spec_record` — писать/расширять спеки, create-or-update с CAS по `version` (как текущий kb)
- `graph_reindex` — пересобрать граф из код+спеки (инкрементально)
- существующие `edit_file`/`write_file`/`run_command`/debug-* — без изменений

Текущие `kb_*` остаются как тонкий фасад над `graph_query`/`spec_*` (обратная совместимость).

---

## 9. Изменения доктрины (SystemPrompt)

- Любой вопрос «где/что/почему/что регулирует» → сперва `graph_query`/`context_bundle`, не grep.
- Факты Категории Б → **всегда** `resolve_ref`, **никогда** не вспоминать и не копировать.
- Перед написанием кода подтянуть `governed_by` (INVARIANT/POLICY/LESSON) и применить как
  жёсткие ограничения.
- После правок → `spec_validate` + сборка/тесты (`run_command`) + `graph_reindex`.
- При неудаче → `spec_record` LESSON.
- Эскалация на Author tier — только для авторской работы, с готовым bundle.

---

## 10. Жизненный цикл фичи («строить по XML»)

1. Автор пишет/расширяет `spec/`: `INVARIANT` + `CONTRACT ref=…` + `POLICY`.
2. Navigator: `context_bundle` → спека + резолвленные контракты + governing-правила + соседи.
3. Author: пишет код, удовлетворяющий инвариантам, применяя полиси.
4. Navigator: `spec_validate` + build/tests + `graph_reindex`.
5. На грабли → `LESSON`.

---

## 11. Грациозная деградация

Нет `spec/` и графа → geai падает на текущие оси + PSI-навигацию. GRACE **усиливает**, но не
является обязательным: маленький проект работает и без спек. Граф строится инкрементально, по
мере касания узлов, а не «весь проект сразу».

## 12. Фазы реализации (предложение)

- **Ф1 — Якорный хребет. ✅ СДЕЛАНО.** `AnchorResolver` SPI (`anchor/`), резолверы
  `file:`/`psi:`/`openapi:`, диспетчер `AnchorResolvers`, инструмент `resolve_ref`
  (`tools/grace/`), правка доктрины. PSI-резолвер тянет `com.intellij.java` только на компиляции
  (без жёсткого `<depends>` — плагин грузится и в не-JVM IDE, `psi:` там отдаёт чистую ошибку).
  *Даёт ~80% эффекта для дешёвых моделей.*
- **Ф2 — Spec-слой. ✅ СДЕЛАНО.** Модель `spec/` (`SpecModel`/`SpecStore`, JDOM, один файл на
  spec id), инструменты `spec_list`/`spec_lookup`/`spec_record`/`spec_validate`, правка доктрины.
  Ссылочные items (CONTRACT/GOVERNED_BY) штампуются hash-базлайном при записи; `spec_validate`
  re-резолвит якоря и репортит OK/DRIFT/BROKEN/NO-BASELINE. Категория A заработала.
- **Ф3 — Граф. ✅ СДЕЛАНО.** `graph/` пакет: `GraphModel` (NodeKind/EdgeKind), `GeaiGraphStore`
  (`.geai/graph/graph.xml`, кэш + JDOM), `GraphIndexer` (PSI: FILE→class→method + IMPLEMENTS,
  bounded `MAX_NODES`, деградация на не-JVM; + governance из спек: REFS/GOVERNED_BY). Инструменты
  `graph_query`/`graph_neighbors`/`graph_reindex` + доктрина. *Call-рёбра (calls/reads/writes)
  отложены — дорогой проход, не нужен для governance-навигации.*
- **Ф4 — Graph-RAG bundle. ✅ СДЕЛАНО.** `bundle/` пакет: `Ranker` SPI + `DeterministicRanker`
  (hops + term-overlap + kind-prior) + `Rankers` (шов под вектор, флаг `graceVectorRanker`),
  `ContextBundler` (seed→expand(BFS)→rank→resolve→pack: правила A дословно + контракты B живьём +
  neighborhood). Инструмент `context_bundle` + доктрина. Векторный ранкер плагинится в `Rankers`.
- **Ф5 — Маршрутизация моделей. ✅ СДЕЛАНО.** Тиринг opt-in (`tieredRoutingEnabled`,
  `navigatorModel`): цикл идёт на дешёвой navigator-модели (`loopModel()`), авторинг кода —
  через `escalate_author` на сильной main-модели (`authorModel()`), тир = имя модели в
  `ChatRequest` (тот же провайдер/ключ; кросс-провайдер — позже). Author-доктрина без
  инструментов; условная routing-подсказка в системном промпте. Один ключ.

Каждая фаза самостоятельна и проверяема сборкой.

> **UI:** `tieredRoutingEnabled` / `navigatorModel` настраиваются на вкладке **Advanced** в
> `GeaiSettingsConfigurable`. `graceVectorRanker` остаётся флагом уровня кода (state + `Rankers`),
> но из UI убран — вместе с telemetry-dev и model-prices, чтобы экран настроек «просто работал»
> на здравых дефолтах (вектор-слой включится, когда появятся эмбеддинги — см. §13.5).

## 13. Открытые вопросы (развилки)

1. **Формат спек** — XML подтверждён; нужен финальный словарь тегов (узлы §3 ↔ теги).
2. **Хранение графа** — производный + gitignored (рекомендую) vs коммитить.
3. **Старт реализации** — Ф1 (якоря) первым (рекомендую: фундамент) vs сразу граф.
4. **Ребинд якорей** — авто при ренейме vs только флаг в `spec_validate`.
5. **Векторный слой** — *решено:* **шов с первого дня, эмбеддинги инкрементально.** В пайплайн
   `context_bundle` вводится `Ranker` SPI; дефолтная реализация — детерминированный ранкер
   (graph distance + tag/name match + recency), без внешних зависимостей. `VectorRanker` —
   подключаемая реализация того же SPI; вектор узла считается при индексации и **растёт со
   знанием проекта**, включается флагом. Архитектурно вектор присутствует сразу, расход —
   только когда есть что ранжировать (пустой граф ранжировать незачем).
